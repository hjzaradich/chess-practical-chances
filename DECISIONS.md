# Decisions

Departures from `SPEC.md` and answers to its open questions, one line of reason each. Newest phase last.

## Phase 0

| # | Decision | Reason |
| --- | --- | --- |
| 0.1 | Core language: **Rust** (`ort` 2.0.0-rc.15 + `shakmaty` 0.30), not a Python sidecar. *Pending Henry's approval.* | The Rust spike matches the official `maia3` package to 1.8e-6 on move probabilities and 3.9e-7 on W/D/L, across 42 cases (14 positions × 3 ratings); its top move agrees in all 42 (`spikes/s1_maia_rust`). |
| 0.2 | Maia input = the **last 8 positions**, not just the current FEN. Each slot is mirrored by its own side to move, oldest first, and padded at the front with the earliest position. | That's how the model was built (`history = 8`). Real history changes move probabilities by up to 0.18 compared with feeding the board alone. D barely moves (≤ 0.007). |
| 0.3 | We ship **our own ONNX export** of the official Maia3-5M weights, with history as an input (`spikes/s1_export_and_reference.py`). We don't use the community 5M file. | The community 5M export is accurate (2.2e-6) but repeats the current board 8 times inside the graph, so it can't take history. Only its 79M file has a history input. *Hosting settled in 5.1.* |
| 0.4 | Maia takes **two ratings**: the mover's and the opponent's. At X's tree nodes we pass (R\_X, R\_opponent). D at a ply uses (R\_mover, R\_other). | The spec's single-rating P\_R(m\|n) doesn't match the model; the official UCI wrapper exposes `SelfElo` and `OppoElo`. |
| 0.5 | Cache keys: Stockfish → FEN without move counters + node limit + MultiPV. Maia → the last 8 positions + both ratings. | The spec says "keyed by position (FEN)". That's right for Stockfish and wrong for Maia, whose output depends on history (0.2). |
| 0.6 | Stockfish MultiPV parsing: keep only the last complete line per `multipv` index, and drop repeated moves. | A node-limited search can stop partway through a depth and leave stale lines from the previous depth. The first parser listed the same move twice. |
| 0.7 | Test position for "R+B vs R" is `8/7r/3k4/8/4K3/3B4/8/5R2` (both sides to move). | The first FEN I tried hung a rook to whoever moved first. This one is ~99% drawn for Stockfish with no tactics. |
| 0.8 | Presets *(pending Henry's approval)*: **Quick** k=1, p=0.90, 50k nodes. **Standard** (default) k=2, p=0.90, 50k nodes. **Deep** k=2, p=0.90, 200k nodes. | Measured 80-ply games on this laptop: 0.7–0.9, 3.0–3.4 and 12.4–12.8 min. Deep spends its extra time on nodes, because Stockfish noise is the bigger error at 50k. |
| 0.9 | k=3 is not offered. | 600 tree positions per ply on average (max 2,201), about 26 min per game at 50k nodes. |
| 0.10 | Phase 1: clear Stockfish's hash before every search (`ucinewgame`), so each result depends only on position + node limit. | Identical settings gave v\* values differing by 0.06 on average (max 0.5) on a sharp game, because of leftover hash state. This breaks reproducibility and the cache. |
| 0.11 | Phase 1: take v\* from a MultiPV-1 search like the leaves. Run MultiPV separately, only for the stability diagnostic. | At equal nodes, MultiPV 5 reaches 3–4 plies less depth, which would bias T = v\* − V. |
| 0.12 | Stockfish: one single-threaded process per physical core (4 here). | Throughput at 200k nodes: 3.0 / 4.4 / 6.1 / 6.8 searches/s with 1 / 2 / 4 / 8 processes. |

## Phase 1

| # | Decision | Reason |
| --- | --- | --- |
| 1.1 | Henry approved Phase 0 (Rust core, presets 0.8) on 2026-11-11. Hosting the Maia ONNX file is still open, so the CLI takes `--maia-model` (default `models/maia3-5m.history.fp32.onnx`), built by `tools/export_maia_onnx.py`. | First-run download is Phase 3. |
| 1.2 | Output fields: `ply` = half-moves played (0 = start); `san`/`uci` = the move that led here. `v_star` is from White's point of view; each `trickiness`/`diagnostics` entry from that player's; `likely_moves[].v` from the mover's. | The spec's example leaves the viewpoints open. |
| 1.3 | Diagnostics are computed at each player's next decision point: the root for the side to move, otherwise the position after Stockfish's best reply. The added field `at_ply_offset` (0 or 1) says which. | Stability and trap mass only make sense where that player chooses a move. |
| 1.4 | Trap mass counts Maia's raw probability on *expanded* moves (the top-p set) whose value is more than δ below the value after Stockfish's best move. Both values come from the same kind of search (MultiPV 1 on the resulting position). | Unexpanded moves (≤ 1−p of the mass) have no value. Comparing against the MultiPV score would mix search depths (0.11). |
| 1.5 | `stable_moves` is capped at `--multipv` (default 5). | It's counted from the MultiPV lines. |
| 1.6 | Best move = the move of the chosen MultiPV-1 line, not the `bestmove` token. | Keeps the move and its value from the same line. They differ only when a search stops on a fail-high. |
| 1.7 | `settings` also records ε, δ, MultiPV, both ratings, the Stockfish name and the Maia file + SHA-256 prefix. | "Traceable numbers". |
| 1.8 | Game end inside trees: checkmate, stalemate and insufficient material are scored exactly. Threefold repetition and the 50-move rule are **not** detected: Stockfish gets a bare FEN with no history. | Known gap. It matters only in shuffling endgames. |
| 1.9 | PGN: main line only (variations and comments ignored); first game unless `--game N`; ratings from WhiteElo/BlackElo, with "?" or missing → 1500. | Spec. |
| 1.10 | Stockfish workers default to logical cores / 2 (4 on Henry's laptop); hash 16 MB per process. | 0.12. A small hash is enough at 50k nodes, and clearing it is cheap. |
| 1.11 | The cache defaults to `trickiness-cache.sqlite` in the working directory. | Phase 3 moves it to the app's data folder. |
| 1.12 | `ort` is pinned to `=2.0.0-rc.15`, a pre-release. | It's the current release line; pinning stops a breaking rc update. Revisit when 2.0 is stable. |

## Phase 2

| # | Decision | Reason |
| --- | --- | --- |
| 2.1 | Data: the first 52,422 games of the Lichess standard rated database for 2026-10 (streamed, not downloaded in full). Kept: rated Blitz/Rapid/Classical, base time ≥ 3 min, ended normally or on time, ≥ 20 plies, **both** players in the band. 3,000 games per band: 1400–1600 and 1900–2100 (`tools/fetch_lichess_sample.py`). | The spec asks for "a few thousand games" per band. The month is after Maia-3's training data, so the test is out of sample. |
| 2.2 | T test: **one position per game** (uniform over ply 6 to the end, seeded), 400 games per band = 800 (T, realized loss) pairs per band, all six (k, p) combinations on the same positions. | Every ply of thousands of games costs ~2.5 s × 80 plies × 6,000 games ≈ 330 hours on this laptop. One position per game also keeps the samples independent. |
| 2.3 | Realized loss for X = Σ over X's next k moves of v\*\_X(before) − v\*\_X(after), with v\* from the same Stockfish settings as the core (50k nodes, cleared hash). If the game ends sooner, the moves available are summed. | Spec definition. |
| 2.4 | D test: Maia's D at ply 30 (after move 15, ratings = the game's), against whether the game was drawn, for every game reaching ply 30 (2,791 and 2,877 games). Stockfish's own draw probability is shown for comparison. | Spec ("positions around move 15"). |
| 2.5 | Sanity positions: 20 in `validation/positions.yaml`. Five Purpose-table rows, each with 3–6 positions; all endgames checked with Stockfish at 3M nodes, and those with ≤ 7 pieces checked again against the Lichess tablebase. | Spec, step 1. Henry can swap positions. |
| 2.6 | Endgame cross-check with exact values: for the ≤ 7-piece sanity positions, T was recomputed with tablebase values in place of Stockfish (`validation/results/tablebase_check.log`). | Separates "the metric is wrong" from "the test position is wrong" (see the report). |
| 2.7 | Tuned values, **approved by Henry 2026-11-12** (now the CLI defaults): **k = 2, p = 0.9** (unchanged), **ε = 0.01**, **δ = 0.05**. | k and p: every setting falls within the same bootstrap interval of calibration error, so keep Standard (k = 2 sees two-move combinations). ε: 0.01 is within noise of the best fit (0.005) and above what 50k-node Stockfish can separate. δ: the fit improves as δ → 0.01 (rank corr +0.55 vs +0.48 at 0.05), but then "trap mass" just means "any inaccuracy". `validation/REPORT.md` §4. |
| 2.8 | The spec's sanity table is wrong in two rows. "Blocked pawns, active kings ≈ 0" holds only when kings can't get in; R+B vs R "high for the defender" is false at k = 2 (exact tablebase T is 0–0.16). Positions and checks are kept as written; the report explains the failures rather than editing them away. | Tablebase-exact T matches ours in 3 of 4 checked cases (`validation/results/tablebase_check.log`). |
| 2.9 | Henry chose (2026-11-12): T keeps its k-move meaning. SPEC.md's R+B vs R row now reads "defender above the attacker, and falling as rating rises" instead of "high for the defender"; the Phase 2 ordering test changed to match. `validation/sanity_checks.py` checks the new wording. | Exact tablebase T at k = 2 is 0–0.16 for the defender: club players rarely lose R+B vs R in the next two moves, but the small per-move risk compounds over a long defence. Our T now passes all four R+B vs R checks at k = 2 (defender 0.100 → 0.079 → 0.043 at 1100/1500/1900; attacker ≤ 0.003). At k = 1 the defender's T is ~0.002, another reason to keep k = 2. |
| 2.10 | Henry chose (2026-11-12): SPEC.md's first row now reads "blocked pawns where neither king can get in" instead of "with active kings". `validation/positions.yaml` has four sealed walls (each verified: neither king can cross, and every legal move keeps the draw). The two king-and-pawn positions where a king can get in moved to an unchecked category, `kp_king_can_enter`. | When a king can get in, one wrong king move loses, and tablebase-exact T agrees with ours (0.34 vs 0.30 at 1100). All four sealed walls give T = 0.000 at every rating. |
| 2.11 | Henry chose (2026-11-12): Syzygy tablebases are used **if present**. Folder from `--syzygy`, else `$TRICKINESS_SYZYGY`, else `tablebases/` if it exists. They count as in use only when Stockfish reports finding tables; then the engine name becomes e.g. "Stockfish 19 + Syzygy 5-man", which flows into the cache keys and every result's `settings.stockfish`. No tablebases → behaviour unchanged (verified: the cached Kasparov run is byte-identical). Not bundled or downloaded by the app. | Fixes the one case where T was wrong in Phase 2 (R+B vs R #2 with the attacker to move) and makes ≤ 5-piece endgames exact, without forcing a ~1 GB download on every install. |

## Phase 3

| # | Decision | Reason |
| --- | --- | --- |
| 3.1 | Tauri v2 + React 19 + TypeScript in `app/`. The Rust core is linked into the app (no Python sidecar, 0.1). The core streams one `ply` event per ply carrying the same JSON object as the CLI's lines; `analysis-done` ends a run. | Spec: the GUI only starts the core and draws what it streams. |
| 3.2 | Board: **chessground 9 (GPL-3.0-or-later)**, not react-chessboard (MIT). | License check: GPL-3.0 is compatible with this app's AGPL-3.0 (GPLv3 §13), so either works. chessground has built-in arrows (used for Maia's likely moves), is Lichess's own board, and is actively maintained. |
| 3.3 | Chart: Recharts 3 (MIT). v\*, D, T\_White and T\_Black share one 0–1 axis. Colors follow the reference categorical order (blue, orange, aqua, yellow), with a legend and a tooltip giving all four values. | All four are probabilities or expected scores, so one axis is honest (not a dual axis). |
| 3.4 | Output schema extended: each `diagnostics` entry gains `decision_fen`, `via` (the opponent's best reply, SAN), `best_value` and `moves` (that player's likely moves); every likely move gains `loses` (> δ below the best). `likely_moves` stays for the side to move. | The breakdown shows likely moves *for each player* (spec step 4), and the GUI must not do chess math, so the core decides what counts as losing. |
| 3.5 | Stockfish ships as a Tauri sidecar (`binaries/stockfish-<triple>.exe`, copied from `engines/`), with its GPL license, authors list and exact source link in `licenses/` (bundled as resources). | GPL-3.0 requires shipping the license and offering the corresponding source. |
| 3.6 | First-run model: the download flow is built (size shown before downloading via HEAD, progress, full SHA-256 check), but **no hosting URL is set** (`MAIA_MODEL_URL = None`; `TRICKINESS_MAIA_URL` overrides). Until then: "Locate model file…" checks that the file loads, then copies it into the app data folder. Dev builds also find `models/` in the checkout. | Hosting was Henry's decision (0.3, 1.1); settled in 5.1. |
| 3.7 | Data lives in `%APPDATA%\app.trickiness.desktop`: `cache.sqlite`, `results\<key>.jsonl` (key = game + every setting + engine and model ids), `models\`, optional `tablebases\` (2.11). A run writes `<key>.part` and renames it only on completion, so cancelled or failed runs never look finished. | Spec step 5: results saved next to the cache so reopening is instant. Verified: reopening Kasparov–Topalov loaded 88 plies at once. |
| 3.8 | Cancel is checked before every Stockfish or Maia batch; the ply in progress is discarded. Measured latency: ~2 s at Standard. | Waiting for the ply to finish could take 10+ s on Deep. |
| 3.9 | The GUI uses the approved ε = 0.01, δ = 0.05, d = 0.5 and MultiPV 5, shown in the settings line on every breakdown. Presets map to 0.8. | Spec: "Always show the settings used". |
| 3.10 | Move list: a small dot after a move when the player who made it faced T ≥ 0.2 there. | A display aid for finding the hard moments; no new math (it reads T). |
| 3.11 | Theme follows the OS (light/dark), with tokens in `app/src/styles.css`. The app identifier is `app.trickiness.desktop`. | Windows first; nothing used blocks macOS/Linux builds. |
| 3.12 | Henry asked for it (2026-11-12): a **playable board**, minimal version. "New board" starts from the starting position; on any game position, playing the game's next move steps forward in the game, and any other move opens **one side line** (no variation tree), discarded by "Back to game" or Esc. Each line position is analysed on demand at the toolbar's ratings and preset, and shown in the breakdown and arrows; the chart stays the game's. Legal moves and move results come from the core (`legal_moves`, `play_move`); `analyze_position` runs one ply with the real move history. A newer request supersedes an older one ("superseded"); while a game analysis runs, positions share its engines. | Beyond the spec, approved by Henry. Kept minimal: a single side line gives most of "try out lines" without variation-tree UI. The GUI still does no chess math. Tested in the running app: following the game, branching, replacing a move, back to game, rapid moves, underpromotion (bxa8=N). |

## Phase 4

| # | Decision | Reason |
| --- | --- | --- |
| 4.1 | Q(m) as in SPEC.md, in `crates/core/src/practical.rs`. Candidates: Stockfish's top 5 (MultiPV) plus Maia's top 5 for the player to move. Opponent replies: Maia at their rating, top-p (0.9) renormalised, weight (1−λ), plus λ on Stockfish's best reply r\* (added if Maia didn't list it). After the reply: **horizon 1**, i.e. one more decision by the player with Maia sharpened by **τ = 0.7**, then the opponent's best reply and a leaf. | The spec leaves the horizon and τ open; these are the cheapest settings that include "X can't count on finding every only-move" (~15 s per position at Standard). |
| 4.2 | "Relies on" = Maia's chance that the opponent plays a reply more than δ (0.05) better for the player than r\*. "Practical best … +x" is measured against the objective best move's **practical** value, so both numbers assume the same opponent. | The spec's example mixes a practical number with an objective one; comparing like with like says what the choice gains against *this* opponent. |
| 4.3 | **Gate failed: 1 of 8 traps as specified** (`validation/PHASE4_GATE.md`). An experiment scoring leaves with Maia's value head gives 2 of 8 and fails the other way (traps chosen even at 2300). Kept as an experimental flag, `trickiness practical --leaf maia`; the default is the spec's Stockfish leaves. | Stockfish leaves are too harsh for club players and Maia leaves too lenient for strong ones. Opponent errors count only on the first reply, and candidates can miss the trap. *Pending Henry: options A (rating-calibrated leaves, recommended), B (opponent errs at every reply) or C (keep as specified).* |
| 4.4 | App: the practical-move panel (draw-value slider, the spec's three summary lines, a candidate table, a blue arrow for the practical best) and the `analyze_practical` command are built, and compile and pass the backend tests. **Not yet tried in the running app**; that waits for 4.3. | The panel shows whatever Q is chosen. |
| 4.5 | Henry chose option A (2026-11-13): Q's leaves are **rating-calibrated** (`crates/core/src/leaf.rs`). Ordered logit on Stockfish's eval in pawns (cp at 50k nodes; mate = ±12), with rating level, rating gap and material terms. Fitted on 8,000 Lichess games, 800–2399, 28,583 positions (`validation/fit_leaf_model.py`, `results/calib/leaf_model.json`). Default for `trickiness practical` and the app; `--leaf engine` gives SPEC.md's literal Q, `--leaf maia` the 4.3 experiment. T is unchanged (Stockfish leaves). | Held-out log loss 0.80 vs 7.5 for Stockfish's W/D/L (Brier 0.211 vs 0.268), calibrated in every rating group. A first fit on Stockfish's W/D/L failed (58% of positions read as decided), so the core now keeps `cp`/`mate` on every engine line; the engine cache key moved to `sf2` so older entries without them aren't reused. |
| 4.6 | Gate trap set v2 (`validation/traps.yaml`; v1 kept as `traps_v1.yaml`): Kieninger and Elephant removed (their trap moves are objectively best/equal); Wayward Queen, Albin and Smith-Morra added. Maia contributes **8** candidates (was 5). | A trap that costs nothing can't "stop at high ratings". Fishing-pole …Ng4 is still never a candidate. |
| 4.7 | **Gate, calibrated leaves: strict test 1 of 9; trend test 7 of 8** (the trap's practical margin falls as the opponent's rating rises), against 1 of 9 and 3 of 8 with Stockfish leaves (`validation/PHASE4_GATE.md`, round 2). *Pending Henry:* restate the gate as the trend and show a "practical best" only above a clear margin (recommended), add option B for multi-step traps, or keep the strict gate. | On a human scale, opening moves sit within a few hundredths, so "#1 or not" is a knife edge; multi-step traps need the opponent's second mistake, which Q as specified doesn't model. |
| 4.8 | Henry chose (2026-11-13): the Phase 4 gate is **restated as a trend**. On traps whose trap move costs something objectively, the trap move's practical margin over the best other candidate must fall as the opponent's rating rises (lower at 2300 than at 800, no step up by more than 0.005). SPEC.md updated, original wording kept there. **Result: 7 of 9 pass** with calibrated leaves (1 of 9 with Stockfish leaves); the fails are fishing pole (never a candidate) and Siberian (wrong direction). Also: a move is shown as the practical best only if it beats the objective best by **≥ 0.02** (`PracticalParams.margin`; the core reports `edge` and `clear`), otherwise "no clear edge over the engine move". | The original test hinged on margins of a few thousandths. Checked in the running app: Scholar's position at 800 gives Qh5, +0.06 over Nf3, relying on Black missing …g6 (800s miss it 19%); at 2300, "no clear edge over Nf3" (+0.01). The draw slider recomputes from cache. |
